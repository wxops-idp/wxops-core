## Highlights

**The tenant kinds move into the team's namespace, and the old kinds are archived.** `XApp` and `XDatabase` (`tenant.wxops.cloud`, a new API group) are created in a team's own
namespace, so the namespace decides where they run and who owns them — no `namespace`, `owner` or `cluster` field to type, and `owner-seal` and `scope: owned` reach them the
way they reach any namespaced object. `XPolicy` and `XDatabaseCluster` replace `XPlatformPolicy` and `XPlatformDatabaseCluster` under names that no longer repeat the group
([ADR-005](../development-docs/adr/005-kind-ownership-scope-and-naming.md), [RFC-010](../development-docs/rfc/010-namespaced-tenant-kinds.md)). The four old kinds are removed
in this release — **breaking** — and only safe after their XRs have moved: see *Upgrade notes*, first.

Around it:

- **`env-gate` also guards an application's own environment** — a second Kyverno policy, `wxops-<name>-apps`, for an `XApp` or `XDatabase` whose `environment` is guarded, in any
  namespace. An existing `env-gate` starts enforcing it as soon as those kinds exist.
- **`kubectl get wxops -A`** lists what teams run: `XApp` and `XDatabase` carry the `wxops` category, in every namespace. The platform's cluster-scoped kinds stay
  out of it on purpose; `kubectl get composite -A` lists every composite.
- **`environment` is per application and optional**, any name — a team may run one environment, two, or none; promotion is a Git change between overlays.

What those rows mean:

- **`platform-policy`, `platform-database-clusters`, `tenant-app`, `tenant-database` · `breaking`: archived.** Each is replaced by `policy`, `database-cluster`, `app` and `database`,
  which were added beside it and served for a while. Removing a package removes its XRD, **and deleting an XRD deletes every XR of the kind** — the real resources behind them (a
  Kyverno policy, a CNPG cluster, a Deployment, a database) are only safe if the XRs were handed over first, because the handover is what stops the old objects deleting them.
  **Rolling back** to `release-2026-11-09` reinstalls the old XRDs, but the XRs that were deleted do not come back.
- **The new packages · `safe`.** `database-cluster`, `policy`, `app` and `database` are new. Every other package is unchanged and not rebuilt: an earlier draft of this release
  added the `wxops` category to their XRDs, which the API server refuses (`spec.names: Invalid value: Value is immutable`), so it was taken out and `tests/api_compat.py` now
  treats any change to a released XRD's `spec.names` as breaking.
- **Behaviour that changes without a breaking row:**
  - **`env-gate`** now renders a second policy and enforces on `XApp` and `XDatabase` environments.
  - **`wxops:platform-edit`** no longer writes the tenant kinds (they are namespaced and written by team personas); **`wxops:platform-admin`** writes the whole `tenant.wxops.cloud`
    group. `wxops:piece:platform-tenant-write` is gone, and the persona roles gain `wxops:piece:persona-write-tenant` and `persona-read-tenant`.

## Upgrade notes

1. **Move every XR first.** On each cluster, with the old Configurations still installed, run the handover in
   [migrating to the new kinds](../docs/user-guide/migrating-to-new-kinds.md) — in order: policies, database clusters, apps, databases (a dedicated database last). Then:

   ```bash
   kubectl get xplatformpolicies,xplatformdatabaseclusters,xtenantapps,xtenantdatabases -A --no-headers 2>/dev/null   # must print nothing
   ```

   Also check your GitOps repository for manifests of the old kinds: `git grep -E 'XPlatformPolicy|XPlatformDatabaseCluster|XTenantApp|XTenantDatabase'`.
2. **Apply the shared pieces** — `make providers-config` (the hub's `ClusterProviderConfig`, which the namespaced kinds use) and `make providers-rbac` (the persona and platform pieces).
   And make sure the `ClusterSecretStore` **`vault-tenant`** exists, scoped to OpenBao's `tenants/` mount: `XDatabase` pushes its credentials through it, and the Secrets an
   `XApp` reads with `secretsFrom` come through it.
3. **Install the new packages** — `make install` or `make install-dev`; `database-cluster` before `database`. An `XApp` or `XDatabase` in a namespace with no `wxops.cloud/owner` renders
   nothing and says so; label the team's namespaces first (GitOps, platform team).
4. **Remove the old Configurations**, only after step 1 printed nothing — `make install` never deletes one:

   ```bash
   kubectl delete configuration.pkg.crossplane.io wxops-core-platform-policy wxops-core-platform-database-clusters wxops-core-tenant-app wxops-core-tenant-database
   kubectl delete clusterrole wxops:piece:platform-tenant-write --ignore-not-found
   ```

   An Argo CD `Application` with pruning does this by itself once `package/install` stops listing them.
5. **A shared `XDatabase`'s cluster is chosen by the platform** — a stable hash of owner and name, kept in `status.clusterRef`. A migrated database stays where it was because the
   handover renders the same objects; a new one lands wherever the hash puts it.

## Known issues

- **The new kinds have not been run on a cluster in full.** Offline they render, validate and replay cleanly. On the sandbox, the policy handover is proven, and so is `env-gate`
  on an application's own environment (`./run.sh env-gate`, 21 of 21 rows, the `XApp` rows included). Still to run: namespaced `Object`s through the `ClusterProviderConfig`; an
  `Object` writing into the CNPG namespace and a cluster-scoped `Role`; the namespaced `Usage`; adopting a database with no password rotation and no new OpenBao version. Provider-kubernetes v1.2.1's code allows each; the API server and RBAC are the parts it cannot answer.
- **`XDatabase` placement is a stable spread, not least-loaded** — it does not read other teams' databases, since a namespaced kind is not reliably listable across namespaces.
- **`XDatabase` writes through the `vault-tenant` `ClusterSecretStore`**, scoped to the `tenants/` mount; a tenant cannot name another. It must exist before the first
  `XDatabase`: without it the `PushSecret` fails to find its store. An `XTenantDatabase` that relied on the old default, `vault-cluster-store`, changes store when it moves.
- **A dedicated database needs its cluster first**: an `XDatabaseCluster` named `<owner>-<dbName>-cluster`, labelled `wxops.cloud/owner`, `shared: false`.
- **An application or database that is already running is never deleted by a missing owner label**: its reconcile fails with the reason and what exists is left as it is.
- **A namespaced `Object` has no `deletionPolicy`**; the compositions orphan with `managementPolicies` instead (provider-kubernetes v1.2.1).
- **`wxops:platform-edit` has no write piece today.** It stays so a binding that names it keeps working.
