# RFC-008: The secret store as a platform API — OpenBao mounts, policies and access as resources

## Status
<!-- Draft | In review | Accepted | Declined | Withdrawn | Implemented — and the GitHub issue that carries the discussion, e.g. "Draft · #42" -->
Draft

## Summary

Every Core package that touches a credential already depends on a secret store being configured a particular way, and **nothing in this
repository configures it**. `XScmConnection` names a store called `vault-platform`; the [Vault path convention](../../CLAUDE.md#vault-path-convention)
assumes `platform/` and `tenants/` mounts; [RFC-004](004-dex-identity-and-portal-authentication.md) and
[RFC-006](006-cloudflare-r2-object-storage-and-backup.md) add paths under both. All of it is created today by a `bao` session or a Helm
`postStart` hook — the one piece of platform state nothing converges on.

**The purpose of this RFC is to turn that dependency into part of the platform API.** Two small kinds — `XSecretStore` (a KV mount, the ESO
store scoped to it, and the role ESO logs in with) and `XSecretAccess` (one consumer's policy and auth role for one slice of a mount) —
so that giving Dex, an SCM connection or a new tenant access to secrets is a resource somebody reviews, not a command somebody ran once.

Mechanically it reuses what RFC-003 already built: a `provider-opentofu` `Workspace` running the `hashicorp/vault` Terraform provider.
That adds **no new API surface** — the alternative, `upbound/provider-vault`, installs **259 CRDs** to reach the same provider.

## Motivation

1. **The contract is implicit, so it breaks late and quietly.** If the store is missing, scoped to the wrong mount, or its policy omits a
   path, nothing fails at admission. It fails inside a provider pod, as a 403 on a reconcile nobody is watching, and the XR simply never
   becomes ready.
2. **Access is the hard half, and it is hand-written.** ESO needs a Kubernetes auth role bound to its ServiceAccount plus a policy scoped to
   the mount; every new consumer — Dex, OAuth2 Proxy, a tenant's app — needs another. Hand-edited policy HCL is the least reviewable, most
   drift-prone part of the platform.
3. **Onboarding a tenant should not require a `bao` session.** Everything else about a tenant is a resource. This is the exception, and it is
   the exception that holds the secret material.
4. **A `postStart` hook is not GitOps.** It runs once, corrects no drift, and leaves nothing in a diff. Two clusters configured by hand are
   two different clusters.

## Detailed Design

### What the user gets — the whole point

```yaml
apiVersion: platform.wxops.cloud/v1alpha1
kind: XSecretStore              # platform-owned: a mount, the ESO store on it, and ESO's way in
metadata:
  name: platform
spec:
  parameters:
    mountPath: platform                 # KV v2. The ESO store is scoped here, which is why every
    storeName: vault-platform           # remoteKey in this repo is mount-relative.
    esoServiceAccount:
      name: external-secrets
      namespace: external-secrets
status:
  created: true
  ready: true
  storeName: vault-platform             # what XScmConnection.secretStoreRef points at
  mountPath: platform
```

```yaml
apiVersion: platform.wxops.cloud/v1alpha1
kind: XSecretAccess             # one consumer, one slice of one mount
metadata:
  name: dex-read-platform-oauth
spec:
  parameters:
    storeRef: {name: platform}
    pathPrefix: oauth/                  # relative to the mount
    capabilities: read                  # read | read-write
    serviceAccounts:
      - {name: dex, namespace: dex}
status:
  created: true
  ready: true
  policyName: wxops-dex-read-platform-oauth
  roleName: wxops-dex-read-platform-oauth
```

That is the entire user-facing surface: two kinds, nine fields. The breadth of the Vault API stays available inside the module, but a
platform engineer onboarding Dex writes the second object above and reviews it in a pull request.

### Which OpenBao APIs this drives

| What | Terraform resource | OpenBao API |
|---|---|---|
| KV v2 mount | `vault_mount` | `PUT /v1/sys/mounts/<path>` |
| Policy | `vault_policy` | `PUT /v1/sys/policies/acl/<name>` |
| Kubernetes auth role | `vault_kubernetes_auth_backend_role` | `PUT /v1/auth/<path>/role/<name>` |
| (read) mount accessor for the ESO store | `vault_auth_backend` data | `GET /v1/sys/auth` |

**Enabling the Kubernetes auth backend itself is deliberately *not* here.** It is one store-wide object; two `XSecretStore`s both trying to
enable `auth/kubernetes` would fight over it. It belongs to bootstrap, and both kinds take an `authPath` (default `kubernetes`) that they
only create *roles* under. Naming that trap now is cheaper than discovering it when the second store is created.

### Mechanism, and why not the obvious one

`upbound/provider-vault` is generated by upjet from `hashicorp/terraform-provider-vault` — its own build pins
`TERRAFORM_PROVIDER_SOURCE ?= hashicorp/vault`, `TERRAFORM_PROVIDER_VERSION ?= 5.9.0`. A Workspace runs that same provider, so **no
capability is lost**; what differs is the packaging:

| | Workspace + `hashicorp/vault` (chosen) | `provider-vault` | `provider-http` |
|---|---|---|---|
| New CRDs | **0** — reuses the installed `Workspace` | **259** | 4, untyped |
| Typed schema | yes | yes | no — hand-written JSON bodies |
| Status granularity | per Workspace (coarse) | per object | per request |
| State | an OpenTofu state Secret per Workspace | the CR is the state | none |
| Pinning | we pin the provider in HCL | upjet's cadence (its pin is a mid-2025 commit) | n/a |
| Consistency | same shape as the SCM packages | a second mechanism | a third mechanism |

**One Workspace per scope, never one module for everything.** Removing a resource from a module destroys that object on the next apply, so a
shared module would make one mistake able to take the whole store's configuration with it. One `XSecretStore` and one `XSecretAccess` each
own their own Workspace.

The honest costs of this choice: status is "the module applied" rather than per-object, a single bad resource fails its whole Workspace,
and policy text lives inside that Workspace's state Secret in `crossplane-system` — configuration, not secret values, but a Secret to keep
under the same RBAC review as any other.

### Composition shape

Both kinds follow the SCM pattern exactly — `function-patch-and-transform`, one `Workspace`, inline HCL, `vars[]` from the XR, outputs into
`status`:

- **`XSecretStore`** emits a Workspace (the mount, the policy ESO gets, the auth role bound to ESO's ServiceAccount) plus a
  `provider-kubernetes` `Object` wrapping the ESO `ClusterSecretStore` scoped to that mount. `provider-kubernetes` is already granted
  `clustersecretstores`, so there is no RBAC change.
- **`XSecretAccess`** emits a Workspace: a policy over `<mount>/data/<pathPrefix>*` plus the matching metadata paths, and an auth role bound
  to the named ServiceAccounts.

Ordering is self-healing rather than gated: ESO retries a store whose role does not exist yet, so the only visible effect is a failing
`ClusterSecretStore` for a few seconds. Worth knowing when reading the events, not worth a dependency mechanism.

### The token this needs, and what stays out of band

The Workspace authenticates with a token from a Secret, in the same tfvars shape the SCM connection uses. **Not a root token.** A periodic
token whose policy allows only:

```hcl
path "sys/mounts/*"            { capabilities = ["create", "read", "update", "delete"] }
path "sys/policies/acl/*"      { capabilities = ["create", "read", "update", "delete"] }
path "auth/kubernetes/role/*"  { capabilities = ["create", "read", "update", "delete"] }
```

That can reconfigure the store but **cannot read a single KV value** — a materially smaller blast radius than root, for the same result.

Out of band, and documented as such rather than pretended away: `operator init`, the unseal keys, enabling the Kubernetes auth backend, and
creating this token. The first credential of a secret store cannot come from the store. There is no cycle: the Workspace uses the bootstrap
token, while ESO uses the role the Workspace creates.

### Configuration, not values

| Concern | Owner |
|---|---|
| Mounts, policies, auth roles | this RFC |
| Secret values written from the cluster | ESO `PushSecret` and generators, as every existing package does |
| Bootstrap material (a host token, a first credential) | the operator, with `bao kv put` |

The Vault provider *can* write values (`vault_kv_secret_v2`), and even sourced from a Kubernetes Secret rather than from Git. It is still
forbidden here, for a reason that is not "secrets in Git": ESO already does Kubernetes → store, every package follows it, and two
mechanisms writing the same records is worse than one. An invariant enforces it — no module in these packages may contain a
`vault_kv_secret`, `vault_kv_secret_v2` or `vault_generic_secret` resource.

### Adopting what already exists

The platform already has mounts and a `vault-platform` store in use, and a fresh `vault_mount` would fail with "path is already in use".
Because these objects are few and platform-level, a **static `import` block** in the module is enough — the same mechanism RFC-003 declined
for tenant resources, where the set is dynamic. Phase 1 writes the import for the known mounts once; it is not a per-resource feature.

### Compatibility and change tier

Two new packages, `secret-store` and `secret-access`, `group: platform`, `path: package/platform/…`, `current: unreleased` — `safe`, since
adding a package is additive. No new Crossplane provider, so no new provider RBAC and nothing to add to `providers/`. The Vault Terraform
provider is MPL-2.0, so the runtime stack stays open source ([RFC-002](002-migrate-terraform-to-opentofu.md)).

### Testing

- Goldens: a platform store; a read access; a read-write access; an access naming two ServiceAccounts.
- `_invalid/` cases: unknown `capabilities`, an absolute `pathPrefix` (it is mount-relative), a missing `storeRef`.
- **Invariants:** no KV-writing resource in any module (above); no policy text in `status`; `remoteKey`-shaped paths stay mount-relative.
- `tofu validate` on each extracted module, against the pinned provider.
- Offline tests prove the rendered Workspace only. Whether OpenBao accepts each resource, and whether ESO can then log in, needs a cluster
  with OpenBao — and that is also where the Vault-versus-OpenBao parity question gets answered.

## Drawbacks

- **Coarser status than a native provider**, and one bad resource fails its Workspace. Mitigated by one Workspace per scope; not eliminated.
- **A state Secret per Workspace**, holding policy text. It must survive, and it is one more object under RBAC review.
- **OpenBao is a fork of Vault.** The provider targets Vault's API; pin it and verify `vault_mount`, `vault_policy` and
  `vault_kubernetes_auth_backend_role` against OpenBao rather than assuming parity. The exact KV v2 form (`type = "kv"` with
  `options = { version = "2" }` versus `type = "kv-v2"`) is the first thing to confirm.
- **Policy layout becomes public** to anyone who can read the repo. That is the trade for reviewability, and it is why path *contents* stay
  out of the repo entirely.
- **Three things remain manual** — init, unseal, and the config token — so "all of it is GitOps" would be a false claim.
- **Drift is corrected in batches**, on the provider's re-plan interval, not per object.

## Alternatives

- **`upbound/provider-vault`.** The same underlying provider with per-object status and drift, at 259 CRDs for a handful of mounts and
  policies, plus a second mechanism for external APIs and a dependency on upjet's release cadence. Revisit if per-object status ever
  matters more than API surface — most likely if per-tenant policies grow into the hundreds.
- **`crossplane-contrib/provider-http`.** Four CRDs, and OpenBao's config API is all idempotent `PUT`s, so it fits. Rejected because the
  bodies are untyped JSON with no schema validation, errors arrive as HTTP codes rather than typed conditions, and it is a small project to
  put on the critical path of the secret store.
- **A `postStart` hook or seeding `Job` with the `bao` CLI.** What exists today: simplest, and the reason this RFC exists.
- **A dedicated Vault configuration operator.** Purpose-built, but another controller in a control plane that has chosen Crossplane as its
  only one.
- **Do nothing but document the commands.** Honest, and the right answer for *this* release — see the plan below.

## Rollout Plan

- [ ] **Now, for this release: document the bootstrap.** The `bao` commands for init, unseal, the Kubernetes auth backend, the mounts, the
  ESO store and the config token, in `docs/user-guide/setup.md`, labelled plainly as the one part of the platform that is not GitOps. This
  unblocks SCM and Dex without pretending.
- [ ] **Spike.** The KV v2 resource form against OpenBao; whether the Vault provider can log in via Kubernetes auth instead of a token
  (unverified — it would remove the long-lived token entirely); and what `provider-opentofu`'s re-plan interval actually is.
- [ ] **Phase 1 — `XSecretStore`** for the platform mount, with the static `import` for what already exists, replacing the hand-made store.
- [ ] **Phase 2 — `XSecretAccess`**, then point `XScmConnection.secretStoreRef` and RFC-004's records at the published outputs.
- [ ] **Phase 3 — the tenant mount** and per-tenant access as part of onboarding.
- [ ] **Later** — audit devices, and transit auto-unseal for a second cluster.

On acceptance, one ADR: the secret store's configuration is a platform API driven by the same Workspace engine as vendor APIs, and secret
values are ESO's alone.

## Open Questions

1. **Token or Kubernetes auth** for the Workspace (spike). It decides whether a long-lived credential exists at all, and who rotates it.
2. **One mount with prefixes, or a mount per environment?** RFC-006 chose one Cloudflare account per environment; the symmetric answer here
   would change every `remoteKey` in the repo.
3. **Group placement.** `platform` per [ADR-002](../adr/002-three-api-groups.md), since secrets integration is explicitly not its own
   group — but access control arguably leans `auth`. Placement cannot be changed later without a new kind.
4. **How far `XSecretAccess` goes.** Policy and auth role only, or also the ESO `SecretStore`/`ExternalSecret` the consumer needs? The
   narrow version composes; the wide version is one object per consumer.
5. **Vault as well as OpenBao?** The same provider drives both. Is an adopter running HashiCorp Vault supported, or is OpenBao the only
   store this repo claims?
