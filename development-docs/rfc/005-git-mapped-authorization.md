# RFC-005: Authorization mapped one-to-one to Git — RBAC for who may act, Kyverno ABAC for on what

## Status
<!-- Draft | In review | Accepted | Declined | Withdrawn | Implemented — and the GitHub issue that carries the discussion, e.g. "Draft · #42" -->
Draft

## Summary

Authorize every change to a Core resource from two things that already exist in Git: the person's org and team membership at their
Git vendor (delivered as claims by Dex, [RFC-004](004-dex-identity-and-portal-authentication.md)) and the tenant that owns the
resource. A small, static **RBAC** set answers *who may touch which kinds*; **Kyverno** answers the part RBAC cannot express for
cluster-scoped resources — *whether this subject may touch this owner's resource, in this environment*. All of it is written in
the GitOps repository and reviewed as diffs. Nothing is granted by hand in the cluster, and nothing is generated by a
composition.

## Motivation

[RFC-004](004-dex-identity-and-portal-authentication.md) makes a person's identity and Git memberships available. Nothing yet
uses them:

1. **Every Core kind is cluster-scoped** (`scope: Cluster` on all eight XRDs), so Kubernetes RBAC has no namespace to bind a team
   to. RBAC can grant "create `XTenantApp`", but it cannot say "only for `team-alpha`'s apps" — the only per-object RBAC lever
   is `resourceNames`, which does not help when the name is chosen at creation. Today, anyone allowed to create an XR can create
   it for any tenant.
2. **Ownership is not a uniform field.** Only `XTenantDatabase` has an `owner` parameter (it drives the Vault path); the other
   kinds express ownership as `orgName`, a namespace, or not at all. Any rule about "whose resource is this" has no single
   place to look.
3. **Authorization drifts unless it has one source.** If team membership is duplicated into a cluster-side mapping, the
   duplicate goes stale the first time someone leaves a team. The requirement is that authorization *is* Git state, not a copy
   of it.

Kyverno is already in the stack (`providers/policies/darlane-ttl.yaml`) and is the settled choice for validation and
guardrails ([`_archives/ROADMAP.md`](../_archives/ROADMAP.md)), so this RFC uses it for ABAC rather than adding an engine.

## Detailed Design

### Principles

- **Git is the only place authorization is written.** Policies and RBAC bindings are files in the GitOps repository, reviewed
  as diffs. That is the same reason the [decided rejection](../_archives/ROADMAP.md#decided-and-rejected) keeps RBAC out of compositions.
- **No parallel mapping table.** The link between a Git team and a tenant is a naming convention checked by policy, so there
  is no second copy to drift.
- **Kyverno validates; it does not default and does not generate RBAC.** Defaulting would create a second source of truth
  beside the KCL compositions ([`_archives/ROADMAP.md`](../_archives/ROADMAP.md), *Decided and rejected*). Generating RBAC would need Kyverno's controller to hold
  those permissions — the same privilege-escalation shape the provider-RBAC decision rejects — and would bypass diff review.
- **Small on purpose.** [ADR-001](../adr/001-package-channel-label.md) records why a heavier guardrail system was rejected as
  something one maintainer cannot operate or explain. The policy set here stays at five rules; growth beyond that needs its own
  RFC.

### Attributes

| | Attribute | Source |
|---|---|---|
| **Subject** | groups, connector id | Dex ID token claims, via the API server or the caller (below) |
| **Subject** | writer kind | the requesting user: a person, the Portal, or Argo CD |
| **Resource** | owner | a **required label** `wxops.cloud/owner` on every Core XR |
| **Resource** | environment | `spec.parameters.environment` where the kind has it (`XTenantApp`) |
| **Resource** | kind, target cluster | the XR itself |

The `wxops.cloud/owner` label is the trust anchor and is added to every kind by policy, not by an XRD change, so it is
`safe`-tier. It is required at creation and **immutable**, so a resource cannot be reassigned to escape a rule. Its value is
the Git team's slug — deliberately the same string a namespaced XR's namespace would carry (see Alternatives), so this design
does not paint a later move into a corner. A Kubernetes label value cannot contain `/`, so the owner is a **flat** slug: a GitHub or
Gitea org, or a top-level GitLab group. GitLab subgroup paths (`parent/child`) are not supported in v1, as decided in
[RFC-003](003-scm-connections-and-resources.md#vendor-alignment).

### The one-to-one rule

A subject may write an XR whose `wxops.cloud/owner` is `X` only if their `groups` claim contains the team `X` at the connector
the resource is bound to. Group format follows the [RFC-004 open question](004-dex-identity-and-portal-authentication.md#open-questions)
and is assumed here to be `<connector>:<org>:<team>`. There is no table: team `team-alpha` in the Git org is the owner
`team-alpha`, and removing someone from the team removes their ability the next time their token is issued.

Two tiers, also derived from Git teams rather than stored:

| Group | May do |
|---|---|
| `<org>:<owner>` | create/update the owner's resources in `dev` and `staging` |
| `<org>:<owner>-maintainers` | as above, and `prod` |
| `<org>:platform` | any owner; the break-glass path, audited |

Git teams carry membership, not role, through the claim — so a "maintainer" tier has to be a second team by naming convention.
Whether that is acceptable is an open question.

### Three writers, three enforcement points

A single check does not cover all paths, because Kyverno only sees the *requesting user*, and on some paths the requesting user
is a machine.

| Writer | Requesting user Kyverno sees | Who is authorized, and where |
|---|---|---|
| **Argo CD** applying a commit | the Argo application-controller service account | The person was authorized when the commit was **merged**, by the Git vendor (branch protection, CODEOWNERS on `tenants/<owner>/`). Kyverno checks that the XR's `owner` matches the Argo `Application` that applied it, read from Argo's tracking annotation. Each tenant gets one Application, generated from the Git team list. |
| **Portal** on a user's behalf | the Portal's service account, unless it impersonates | The Portal calls the API impersonating the person and their groups, so Kyverno sees the real subject. The Portal's own account is granted only the ability to impersonate, restricted by `resourceNames` to Dex-shaped group names. |
| **A person directly** (`kubectl`) | the person, if the API server trusts Dex | Kyverno checks `groups` against `owner` as above. Only exists if the API server is configured to trust Dex (RFC-004 open question 5); otherwise this path is closed. |

This is deliberate: on the GitOps path the strongest "1-to-1 with Git" is the Git vendor's own permission on the merge, and
Kyverno's job is to make sure the *content* of the merge cannot claim a tenant its path does not own. That works under every
model in [open decision 3](../_archives/ROADMAP.md#open-decisions) and does not pre-empt it.

### Policy set

Five rules, one policy each, in `providers/policies/` beside the existing one. They are **Kyverno CEL `ValidatingPolicy`**
resources, not `ClusterPolicy`: Kyverno has deprecated `ClusterPolicy` and scheduled its removal for v1.20 with CEL policy
types at parity as of v1.19. The existing `darlane-ttl.yaml` uses `ClusterPolicy` and `CleanupPolicy` and needs the same
migration; that is a follow-up this RFC surfaces rather than absorbs.

| # | Rule | Applies to |
|---|---|---|
| 1 | `wxops.cloud/owner` is present and matches the team-slug pattern | create, all Core kinds |
| 2 | `wxops.cloud/owner` never changes | update, all Core kinds |
| 3 | Writer is authorized for the owner: `groups` contains the owner's team (person / Portal-impersonated), **or** the Argo application that applied it belongs to that owner | create, update |
| 4 | `environment: prod` requires the `-maintainers` group or `platform` | create, update, `XTenantApp` |
| 5 | An `XOIDCClient`'s `redirectUris` sit under a domain its owner is allowed to use | create, update, `XOIDCClient` — closes [RFC-004](004-dex-identity-and-portal-authentication.md) open question 6 |

### RBAC — the coarse layer

Kubernetes RBAC stays small and static, in the GitOps repository: a handful of `ClusterRole`s (`wxops-user`: create/update Core
kinds; `wxops-viewer`: read) bound to the Dex groups. This layer answers "may this kind of subject touch this kind of
resource at all" and Kyverno answers the rest. Platform-owned kinds such as `XScmConnection` ([RFC-003](003-scm-connections-and-resources.md)) get no
tenant `create` verb at all, which plain RBAC can express because they are distinct kinds. Bindings for the group subjects are written in
the GitOps repository like any other manifest; the compositions and Kyverno emit none, keeping the rule in `CLAUDE.md` intact.

### Rollout safety

- Every policy starts in **audit** mode and reports without denying, so existing XRs — none of which carry the label — show up
  as findings before anything is blocked. Labelling them is a one-time change, and only then does a policy move to enforce.
- `failurePolicy` for rules 1–4 is `Fail`. If Kyverno is down, writes to Core kinds are refused, which is the correct
  failure for an authorization control and an availability cost that needs Kyverno running highly available.
- **Break-glass** is the `platform` group, and every use is visible in the audit log; it is not a bypass of the policy engine.

### Compatibility and change tier

No XRD changes. The new required label is a behaviour change to how existing XRs are admitted, so it ships with hand-written
release notes and the audit-first rollout above. Policies are not a Crossplane package and take no `VERSIONS.yaml` entry.

### Testing

Policies get an offline tier in the same spirit as the composition suite: the Kyverno CLI's `test` command runs each policy
against fixture resources **with a supplied requesting user** (name and groups), so every rule has an allowed case and a denied
case per writer kind. Negative cases carry an `# expect:` reason like the existing ones. Two things the offline tier cannot show:
what the API server actually presents as `userInfo` for an impersonated or Dex-authenticated request, and whether Argo's tracking
annotation is present on the object at admission time. Both need a cluster and are spike items.

## Drawbacks

- **This is the machinery the ROADMAP once rejected.** ADR-001 records a guardrail system cancelled for exactly this shape:
  plausible, and more than one person can explain. The five-rule cap is the mitigation, and it is a promise to keep, not a
  mechanism that enforces itself.
- **A label is the trust anchor.** Anyone who can write an XR can write a label; the policy is what makes that safe, so a
  gap in the policy is a gap in tenancy.
- **Claims are a login-time snapshot.** Removal from a Git team takes effect at the next token, not immediately (RFC-004).
- **The Argo path leans on an annotation** whose presence at admission needs confirming, and on Argo being configured with the
  matching resource-tracking method.
- **Naming couples authorization to Git team names**, including the `-maintainers` convention. Renaming a team changes who is
  authorized.
- **Kyverno becomes an availability dependency for every Core write.**
- **Kyverno's CEL policy types are newer.** A reported issue concerns `request.userInfo` resolving to null in some contexts of
  `ValidatingPolicy` ([kyverno#15588](https://github.com/kyverno/kyverno/issues/15588)). The whole design reads `userInfo`, so
  that is a first-order spike item, not a footnote.

## Alternatives

- **Namespaced XRs.** Crossplane v2 makes composite resources namespaced by default and its own guidance reserves cluster scope
  for platform-level resources; with a namespace per tenant, plain RBAC binds a Dex group to a namespace and most of rules 1–4
  disappear. This is the better long-term shape and the strongest argument against this RFC. It is not additive: all eight
  XRDs are `scope: Cluster` today, and a scope change is a new kind, not an evolution of a released one. This RFC takes the
  non-breaking path first and picks the `owner` value so it maps onto a future namespace name one-to-one; **whether to do the
  namespaced move instead of, or after, Kyverno is the central decision for this RFC's review.**
- **`resourceNames` RBAC per XR.** Works only when names are known at grant time, which is exactly what self-service does not
  have.
- **Kyverno `generate` policies for per-tenant RBAC.** Removes the hand-written bindings, but Kyverno's controller would need
  RBAC-writing permissions and the bindings would skip diff review. Rejected on the same grounds as composition-emitted RBAC.
- **Argo CD `AppProject` alone.** Restricts source repos, destinations and kinds per tenant, which is useful and assumed here,
  but it cannot inspect a field or label inside a manifest, so it cannot say an XR's owner is the right one.
- **OPA Gatekeeper or Cedar** in place of Kyverno. Kyverno is already installed and is the ROADMAP's named choice; a second
  policy engine for the same job is cost without a new capability.
- **Authorization only in the Portal.** Simple, but it protects only the path through the Portal; a direct write bypasses it,
  and the check is not reviewable in Git.
- **Do nothing.** Any authenticated person can write any tenant's resources; identity from RFC-004 would then be authentication
  with no authorization behind it.

## Rollout Plan

- [ ] **Spike, before acceptance.** Four questions: does `request.userInfo` work in a Kyverno `ValidatingPolicy` for
  cluster-scoped custom resources on the target version; is Argo's tracking annotation on the object at admission; how does
  impersonation surface groups to Kyverno; what does Kyverno's `failurePolicy: Fail` do to writes during a Kyverno restart.
- [ ] **Decision on namespaced XRs** (Alternatives) recorded before Phase 2, since it changes what Phase 2 builds.
- [ ] **Phase 1 — the label.** Rules 1 and 2, audit mode; label existing XRs; move to enforce.
- [ ] **Phase 2 — the Argo path.** One Application per tenant, generated from the Git team list, and rule 3 for that writer.
- [ ] **Phase 3 — people and the Portal.** Impersonation and Dex trust at the API server, and rule 3 for those writers; the
  static `ClusterRole` set.
- [ ] **Phase 4 — environments and OIDC redirects.** Rules 4 and 5.
- [ ] **Follow-up** — migrate `darlane-ttl.yaml` off `ClusterPolicy` before Kyverno 1.20.

On acceptance, ADRs for: Git-team-slug as the tenant identifier, Kyverno-validate-only (no generate, no defaulting) for
authorization, and the namespaced-versus-cluster-scoped decision, whichever way it goes.

## Open Questions

1. **Namespaced XRs first?** The question above. If yes, this RFC shrinks to RBAC plus a smaller policy set.
2. **The maintainer tier.** Is a `-maintainers` team by naming convention acceptable, or should prod authority come from
   somewhere that carries role explicitly?
3. **Group format.** Depends on the [RFC-004](004-dex-identity-and-portal-authentication.md) decision; rules 3 and 4 match on it.
4. **Token lifetime.** How stale may a Git membership be? A short access token with refresh lowers the lag and raises load on
   Dex and the vendor.
5. **Who may label?** The label is required and immutable, but its first value is written by whoever creates the XR. Rule 3
   makes that safe; is anything else needed for the initial write, such as tenant onboarding creating the label through a
   platform-owned path?
6. **`gitea-*` kinds.** They are being replaced by `XScm*` ([RFC-003](003-scm-connections-and-resources.md)) and later removed, so they need no
   owner label unless they outlive that. They carry `orgName`, not an owner label. Do they take the label like the rest, or does `orgName` stand
   in for it?
7. **Cross-owner references.** A `tenant-app` referencing a shared database cluster, or an `XTenantDatabase` targeting another
   owner's cluster, crosses ownership by design. Is that a rule 6, or handled by the shared-cluster tiering already in place?
8. **Audit.** Where do Kyverno's policy reports and the break-glass events go, and who reads them?
9. **Tenant = org or team? — settled.** The org is the platform and a tenant is a **team inside it**, so the owner label is a team slug, as this
   RFC already assumes. [RFC-003](003-scm-connections-and-resources.md) now says the same; one consequence is that `XScmTeam` is created
   by platform onboarding, not by the tenant it names.
